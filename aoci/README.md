# AOCI — AI-Oriented Code Index

本目录是给「读代码的人和 AI」用的索引层，不是给人从头读的文档。目标只有一个：**在只读 3 个文件的前提下，能安全地改一个功能。**

上游 `AGENTS.md` 已经覆盖了 repo 布局、构建命令和架构背景；本目录不重复，只补三样它没有的东西：**路由（去哪读）、不变量（不能碰什么）、变更登记（改过哪）。**

## 分层

| 层 | 文件 | 回答的问题 | 腐烂速度 |
|---|---|---|---|
| L0 | `index.md` | 我要改 X，该读哪几个文件？ | 慢（功能稳定） |
| L1 | `modules/*.md` | 这个子系统的数据流、契约、扩展点是什么？ | 中（跟随重构） |
| L2 | `invariants.md` | 有哪些一改就炸的硬约束？ | 慢（多是工具链事实） |
| L3 | `index.md#fork-插入点` | 我们改了上游哪些地方？ | 快（随功能演进） |

**刻意不做的事**：全量符号表、调用图、文件依赖图。原因见 `invariants.md#为什么不做符号索引` —— 本仓库 66% 的行是生成物，任何全量索引都会以周为单位腐烂。

## 与 codegraph 的分工

- **codegraph 是派生数据**：回答「谁调用了谁」，可从源码随时重算（`grep` / LSP / `git diff` 已足够），不需要沉淀。
- **AOCI 是沉淀判断**：回答「改这个功能必须先读哪几处、不能破坏什么、改完要跑什么」。这些判断无法从代码自动推导，只能人写、机器校验。

两者不冲突，但优先级不同：符号关系可以重算，判断丢了就要重新踩坑。

## 维护规则

1. **改代码时同步索引**，只改受影响的那一小段，不要把文件重写成通用文档。
2. 任何一次「我踩了坑才发现」的情况，追加到 `invariants.md`，一句话 + 后果，不写故事。
3. 新增入口文件（provider / page / action）时，在 `index.md` 路由表加一行。
4. 索引里引用的路径必须真实存在，用脚本校验：

```bash
python support/scripts/aoci_check.py
```

## 当前覆盖范围

- ✅ 会话/聊天子系统（本 fork 自有代码，无上游参照，最需要索引）
- ✅ 收发链路的插入点（`[FORK]` 标记）
- ⬜ 设备发现、WebRTC、core HTTP 细节 —— 暂由 `AGENTS.md` 承担，需要时再拆模块卡
